# Releasing Cruftless

I release Cruftless from a trusted Mac. GitHub CI checks the source, while the
Developer ID certificate and Apple notarization credentials stay in my local
Keychain.

## Branches and pull requests

- Before adopting this flow, protect `main`: require PRs and the stable
  `Validate` check, block force-push and deletion, require up-to-date branches,
  and use squash merges. In repository settings, allow GitHub Actions to create
  pull requests, automatically delete merged PR branches, and enable immutable
  releases.
- Keep `main` green and releasable.
- Product work uses short-lived `feature/<slug>`, `fix/<slug>`, or
  `chore/<slug>` branches.
- A release uses a temporary `release/<semver>` branch. It contains only the
  version, build number, changelog, and release metadata, merged through a PR.
- This tooling supports stable release versions in `X.Y.Z` form, for example
  `1.1.0`, `1.1.1`, or `2.0.0`. Prerelease versions are not supported.

Fixes found during release preparation go through a normal PR to `main`. After
that fix merges, merge the updated `main` into the existing release branch and
let its PR checks rerun. Do not force-push the release branch. The release-cut
workflow will not start another cut while a release branch or PR is open.

## Local prerequisites

Release signing and notarization run on your trusted Mac, not in GitHub Actions.
Before starting, confirm that:

- Xcode 27, Swift 6.4, `make`, Git, and the release scripts' command-line tools
  are installed. The scripts check for required tools as each command runs.
- The `gh` CLI is authenticated to `danmunoz/cruftless` with permission to
  create releases. Check with `gh auth status`.
- A Developer ID Application identity is available in your Keychain. Check
  with `security find-identity -v -p codesigning`; the archive command can
  select the sole identity or accept `--identity` with its exact displayed
  name.
- The `Cruftless Notary` Keychain profile is configured and usable. Check it
  with `xcrun notarytool history --keychain-profile "Cruftless Notary"`.
- The Cruftless checkout is clean and on `main`, and its local `main` matches
  `origin/main`. The release commands verify this before proceeding.

For the Homebrew step, also install Homebrew and have `curl`, Ruby, Git, and
`gh` authenticated with permission to push and open a PR in
`danmunoz/homebrew-tap`. Use a clean local tap checkout on `main` that matches
`origin/main`.

## Cut a release

1. Run Release · Cut from the GitHub Actions tab on `main`, entering the next
   full SemVer version such as `1.1.0`. The workflow rejects versions that are
   not newer and refuses to start while another release branch or PR is open.
   It creates `release/<version>`, increments the build number once, drafts a
   changelog from release-facing commit subjects, and opens a PR.
2. Review and edit the generated changelog in the PR. Wait for CI, then merge
   through the protected-branch process.
3. On the merged `main` commit, run the local release commands below. The
   archive command verifies the version, build number, commit, clean tree,
   architectures, tests, lint, and unsigned build.
4. Sign and notarize the app, then package and notarize the final DMG. The
   final DMG has its own Developer ID signature.
5. Verify the app and exact DMG with `codesign`, `xcrun stapler validate`,
   and `spctl`.
6. Prepare a Markdown release-notes file for GitHub. It is separate from
   `CHANGELOG.md` and is not generated by the script; use the reviewed changelog
   entry as a starting point and add any user-facing context. Create a draft
   GitHub Release for tag `v<version>`. The script attaches the DMG and SHA-256
   checksum; review the draft, then publish after verification.
7. Verify the public download, then open a Homebrew tap PR using the immutable
   release URL and checksum.

For example, for version `1.1.0`:

```sh
scripts/release/release.sh preflight --version 1.1.0
scripts/release/release.sh archive --version 1.1.0
scripts/release/release.sh notarize-app --version 1.1.0 --notary-profile "Cruftless Notary"
scripts/release/release.sh package-dmg --version 1.1.0
scripts/release/release.sh notarize-dmg --version 1.1.0 --notary-profile "Cruftless Notary"
scripts/release/release.sh verify --version 1.1.0
scripts/release/release.sh draft-release --version 1.1.0 --notes-file /path/to/release-notes.md --confirm-draft
# Review the draft release in GitHub before publishing.
scripts/release/release.sh publish-release --version 1.1.0 --confirm-publish
scripts/release/homebrew-pr.sh --version 1.1.0 --tap-dir /path/to/homebrew-tap --confirm-homebrew-pr
```

Apple credentials, private keys, and Keychain profiles never belong in GitHub
Actions or the repository. Do not paste their contents into logs, issues, or
release notes.

Cruftless/Version.xcconfig is the source of truth for MARKETING_VERSION and
CURRENT_PROJECT_VERSION. The release-cut workflow increments the build number
once when it creates the release PR. Do not add a DMG to the release branch;
the verified artifact is attached to the draft GitHub Release.

## Failure policy

The release scripts deliberately refuse to overwrite output and do not provide
a resume or cleanup command. If archive, signing, notarization, stapling, or
Gatekeeper verification fails, stop without publishing. Preserve
`dist/releases/<version>-<commit>` and its submission records for diagnosis;
inspect the notary submission in the Apple notary service and correct the cause
before choosing a recovery. Do not delete or rename generated files to bypass
the script's checks. If a source fix is needed, merge it to `main` and ask the
release maintainer to determine the next version/build and a safe retry path.

If draft creation reports an error or its completion is uncertain, do not rerun
`draft-release`: creating a GitHub draft may already have reserved tag
`v<version>`, while the local script marker may not have been written. Inspect
the tag, draft, target commit, and assets in GitHub and reconcile them with the
local verification record before taking another action. Do not move or replace
an existing tag.

If Homebrew update fails, do not rerun the script blindly. It may have left a
verification download, local branch, or pushed branch behind, and it refuses
to reuse those. Inspect the tap checkout and GitHub for branch/PR state; verify
the cask version and SHA-256 against the published, verified asset, then resume
manually or ask the release maintainer to reconcile the partial state. If the
published release itself is defective, ship a patch version rather than
replacing its DMG or tag.

If a release cut was started by mistake, close its PR and delete its remote
release branch before cutting another version.

Prereleases are outside this workflow. The release scripts accept only stable
`X.Y.Z` versions and do not set GitHub's prerelease flag; do not use them to
create a prerelease or update Homebrew from one.
